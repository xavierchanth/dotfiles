# Team scope and identity

A Team's responsibility has an explicit scope. Project-scoped Teams serve a semantic work context; repository-scoped Teams serve a repository across the Projects that use it. A Team's saved Project is its home in the harness, not necessarily the boundary of its responsibility. Keep current assignments and participants in live coordination context rather than in reusable skills.

## Names and routing

Prefer a short topic or responsibility followed by “Team.” Rely on the containing Project for organization and Project context; add a qualifier when it resolves genuine ambiguity. Keep workflow choices such as DIVE in the assignment rather than the title, and honor an explicitly requested name.

Names can repeat across Projects. Identify the intended Team using its live Project identity, responsibility, and recent context. If the conversation already establishes the Project, use that context without asking again. Otherwise inspect Project context and ask one concise clarification only when multiple candidates remain plausible. In cross-Project reports, include the Project alongside the short Team name when useful.

## Version Control Teams

Xavier may designate a Version Control Team to coordinate a repository's working-copy state, history, branches or bookmarks, and PR preparation. Resolve its scope from the actual repository identity and assignment, rather than its Project or title alone. A Team may mention an available Version Control Team when asking Xavier how to handle completed changes, but does not infer authority to hand off work or mutate history from that Team's existence.

Working Teams report their changes and validation to Xavier and leave the working copy as it is. When Xavier chooses a Version Control Team for the next step, send it the agreed scope, changed-file manifest, readiness, and evidence. When Xavier chooses inline version-control work, carry out that request within its authorization and coordinate access to any shared working copy. A Team need not determine how many other Teams are active to make this choice.

The [Version Control Coordinator](../roles/version-control-coordinator.md) coordinates selected work with affected contributors before changing shared state. Team assignment does not itself grant checkpoint, publication, merge, or deployment authority.
